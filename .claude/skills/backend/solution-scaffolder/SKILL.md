# Solution Scaffolder

**Principle:** boilerplate is generated by the CLI/scripts, not the LLM. Run these
commands; only fill in domain-specific content afterward.

## 1. Inputs
- `NAME` — the project name in kebab-case (e.g. `acme-billing`); names folders.
- `PROJECT` — solution/root namespace (e.g. `Acme.Billing`); names .NET projects.

## 1a. Repo folder structure (fixed)

The repo root holds the folders `backend`, `frontend`, `mobile` and `docs` —
each created only once it has something in it — plus the root-level files that tie the system together (and, once infrastructure configs
are adopted, the `deploy/` folder the infra skills write to):

```text
<repo>/
├── backend/
│   ├── <name>-api/              # THIS skill: the API solution (sln, src/, tests/)
│   └── <name>-<service>/        # a separate service / microservice — only on request (§7)
├── frontend/
│   ├── <name>-ui/               # the main UI (`frontend-scaffolder`)
│   └── <name>-<ui>-ui/          # a separate UI, named as requested (e.g. admin) — only on request
├── mobile/
│   └── <name>-app/              # the React Native + Expo app (`mobile-scaffolder`) — only on request
├── docs/                        # ALL documentation and related files
│   ├── backend/ARCHITECTURE.md
│   ├── frontend/ARCHITECTURE.md
│   └── mobile/ARCHITECTURE.md
├── docker-compose.yml           # one per repo (`local-dev-environment`)
├── docker-compose.dcproj
└── README.md
```

- Every backend project lives in its **own folder under `backend/`**: the API is
  always `<name>-api`; any other is `<name>-<service>`, where `<service>` is the
  name the user asked for, kebab-cased. Never put a solution, `src/`
  or `tests/` at the repo root or directly in `backend/`.
- Each backend folder is **self-contained**: its own `.sln`, `src/`, `tests/`,
  `Directory.Build.props`, `Directory.Packages.props`, `.dockerignore`. It is
  also its own Docker build context.
- Anything that is documentation — architecture, ADRs, specs, research,
  runbooks — goes under `docs/`, never beside the code or at the root.
- Create `backend/` and `docs/` on first init; `frontend/` and `mobile/` are
  omitted until a UI / a mobile app exists (on-demand rule, §1b).

## 1b. Scaffold only what is needed now (on-demand rule)

The skeleton contains **only what the current requirements use**. Nothing is
added "because we will probably need it":

- No project without code to put in it (no `Worker` until there is real
  background work — see §7).
- No NuGet package without a call site (no Redis/RabbitMQ/S3/Dapper/LLM packages
  until a feature uses them).
- No DI registration, options class, config section, compose service, or
  interface for a dependency that nothing consumes yet.
- No placeholder files (`Class1.cs`, empty folders, sample `WeatherForecast`
  code, the template's `UnitTest1.cs`) — delete what `dotnet new` generates.

Everything else in the constitution's stack is a **catalog of approved choices**,
adopted on demand during development (§7), not a checklist to pre-install.

## 2. Create the solution (run `scripts/scaffold.sh PROJECT` if present, else)

All commands in §2–§8 run **inside `backend/$NAME-api/`** — paths such as
`src/Api` below are relative to that folder.

```bash
P="$PROJECT"
mkdir -p docs "backend/$NAME-api" && cd "backend/$NAME-api"
dotnet new sln -n "$P"

# src
dotnet new classlib -n "$P.Domain"          -o src/Domain          -f net10.0
dotnet new classlib -n "$P.Application"      -o src/Application     -f net10.0
dotnet new classlib -n "$P.Infrastructure"   -o src/Infrastructure  -f net10.0
dotnet new classlib -n "$P.BuildingBlocks"   -o src/BuildingBlocks  -f net10.0
dotnet new web      -n "$P.Api"              -o src/Api             -f net10.0

# tests
dotnet new xunit -n "$P.Domain.UnitTests"               -o tests/Domain.UnitTests           -f net10.0
dotnet new xunit -n "$P.Application.UnitTests"          -o tests/Application.UnitTests       -f net10.0
dotnet new xunit -n "$P.Infrastructure.IntegrationTests" -o tests/Infrastructure.IntegrationTests -f net10.0
dotnet new xunit -n "$P.Api.EndToEndTests"              -o tests/Api.EndToEndTests           -f net10.0
dotnet new xunit -n "$P.ArchitectureTests"              -o tests/ArchitectureTests           -f net10.0

# Add to the solution with EXACTLY two solution folders: src and tests.
# --solution-folder is required: without it the CLI mirrors the on-disk path and
# you end up with nested src/Domain, src/Application, ... folders in the .sln.
dotnet sln "$P.sln" add $(find src   -name '*.csproj') --solution-folder src
dotnet sln "$P.sln" add $(find tests -name '*.csproj') --solution-folder tests
```

Resulting solution view — flat, two folders only:

```
backend/$NAME-api/$P.sln
├── src/            <- solution folder
│   ├── $P.Domain
│   ├── $P.Application
│   ├── $P.Infrastructure
│   ├── $P.BuildingBlocks
│   └── $P.Api
└── tests/          <- solution folder
    ├── $P.Domain.UnitTests
    ├── $P.Application.UnitTests
    ├── $P.Infrastructure.IntegrationTests
    ├── $P.Api.EndToEndTests
    └── $P.ArchitectureTests
```
> Never create per-layer solution folders (`Domain/`, `Application/`,
> `Infrastructure/`, `Presentation/`). Layering is expressed by project names and
> project references, not by .sln nesting. Any new project goes directly under
> `src` or `tests`. The single exception is `docker-compose` (the `.dcproj` added
> by the `local-dev-environment` skill), which sits at the solution root.

## 2b. Pin the language baseline once (`Directory.Build.props` in `backend/$NAME-api/`)

```xml
<Project>
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <LangVersion>latest</LangVersion>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
    <AnalysisLevel>latest-recommended</AnalysisLevel>
  </PropertyGroup>
</Project>
```
> Drop `<TargetFramework>` / `<Nullable>` / `<ImplicitUsings>` from the individual
> `.csproj` files once this exists — one place to bump, no drift. The house code
> style it enables is the table in the `clean-architecture` skill.

## 3. Wire references (dependencies flow INWARD only)

```bash
dotnet add src/Domain        reference src/BuildingBlocks
dotnet add src/Application   reference src/Domain
dotnet add src/Infrastructure reference src/Application   # implements inward interfaces
dotnet add src/Api           reference src/Application src/Infrastructure
```
> Domain must NOT reference Application/Infrastructure/Api. Application must NOT
> reference Infrastructure/Api. Enforced later by ArchitectureTests.

## 4. Pin packages (use `dotnet add package`; let CLI resolve latest stable for .NET 10)

Install **only the baseline** at scaffold time:
- Application: `FluentValidation`, `FluentValidation.DependencyInjectionExtensions`
- Api: `Serilog.AspNetCore`
- Test projects: `FluentAssertions`, `Moq`; `Microsoft.AspNetCore.Mvc.Testing` (E2E).
- ArchitectureTests: `NetArchTest.Rules`.
- Centralize versions in `Directory.Packages.props` (Central Package Management).

Everything else is added **when the first feature that uses it is built** — in
the same change as its call site, never ahead of it:

| Add this…                                                        | …when                                   |
|------------------------------------------------------------------|-----------------------------------------|
| `Microsoft.EntityFrameworkCore` + `Npgsql.EntityFrameworkCore.PostgreSQL` | the first aggregate is persisted |
| `Dapper`                                                         | the first read-side query is written    |
| `StackExchange.Redis`                                            | caching / idempotency store is wired    |
| `RabbitMQ.Client`                                                | the first integration event is published|
| `AWSSDK.S3`                                                      | the first file is stored                |
| OpenTelemetry packages                                           | observability is wired (`observability-stack`) |
| `Testcontainers`                                                 | the first integration test hits a real dependency |
| `WireMock.Net`                                                   | the first external HTTP call is tested  |

## 5. BuildingBlocks shared kernel (create these first — everything depends on them)
- `Result` / `Result<T>` and `Error` (Code, Message, ErrorType) — see
  `cqrs-result-pattern` skill.
- `Entity`, `AggregateRoot`, `ValueObject`, `IDomainEvent`, `IUnitOfWork`.

## 6. DI skeleton (extension methods — keep Program.cs structural)
- `Application/DependencyInjection.cs` → `AddApplication()`
- `Infrastructure/DependencyInjection.cs` → `AddInfrastructure(IConfiguration)`
- `Api/Extensions/PresentationExtensions.cs` → `AddPresentation()` + `MapEndpoints()`

`Program.cs` ends up as: `builder.Services.AddApplication().AddInfrastructure(cfg)
.AddPresentation(); ... app.MapEndpoints(); app.Run();`

The one piece of plumbing in the baseline is the **liveness probe**
(`AddHealthChecks()` + `MapHealthChecks("/alive")`, ASP.NET Core Health Checks —
template in `containerization-cicd`). Never a hand-written health endpoint; the
readiness probe (`/health`) comes later, with the first dependency.

The extension methods start **near-empty** and grow one registration at a time as
dependencies are adopted. Do not pre-register caches, buses, storage clients, or
options for things nothing uses, and keep `appsettings*.json` free of sections
for them.

## 7. Adding things later (on demand)

When a requirement actually calls for it, add the piece in the same change as
the code that uses it: package (§4 table) → interface in Application →
implementation + registration in Infrastructure → compose service and config
keys (`local-dev-environment` skill) → tests.

**Worker** — only once there is real background/long-running work (a consumer,
a scheduled job) that should not run in the API process:

```bash
dotnet new worker -n "$P.Worker" -o src/Worker -f net10.0
dotnet sln "$P.sln" add src/Worker/$P.Worker.csproj --solution-folder src
dotnet add src/Worker reference src/Application src/Infrastructure
```
Then give it a Dockerfile (`containerization-cicd`) and a `worker` compose
service (`local-dev-environment`).

**Separate service / microservice** — only when the user asks for one (a
separately deployed backend with its own codebase; a Worker that shares this
solution's Domain/Application is *not* one). It gets its own folder next to the
API, never a project inside the API's solution:

```bash
SERVICE=notifications                          # the name the user asked for, kebab-case
mkdir -p "backend/$NAME-$SERVICE" && cd "backend/$NAME-$SERVICE"
# then §2–§6 again in this folder, with P="$PROJECT.Notifications"
```
It is a full, self-contained solution (own `.sln`, `src/`, `tests/`,
`Directory.*.props`, Dockerfile, `.dockerignore`) that shares no project
references with `$NAME-api` — services talk over HTTP/messaging. Add its service
to the root `docker-compose.yml` (`local-dev-environment`) on the next free port.
Scaffold only the layers it needs (on-demand rule, §1b).

## 8. Verify before handing off
```bash
dotnet build
dotnet sln list                      # every project listed once, none missing
grep -c 'Project(' "$P.sln"          # sanity: projects + 2 solution folders
```
Open the .sln and confirm only `src` and `tests` appear as solution folders. If a
project landed at the root or in a nested folder, fix it with
`dotnet sln remove <proj>` then re-add using `--solution-folder src|tests`.
Confirm the on-demand rule (§1b): no unused project, package, registration,
config section, or template placeholder file is left in the skeleton.
Confirm the folder structure (§1a): the repo root has only `backend/`,
`frontend/` (if a UI exists), `mobile/` (if a mobile app exists), `docs/` and
root-level files; the solution sits in
`backend/$NAME-api/`.
Hand the green skeleton back to the architect, then proceed to model the first
aggregate and build vertical slices.
